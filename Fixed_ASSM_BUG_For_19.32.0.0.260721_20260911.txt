# Oracle Fixed Bugs: ASSM Bitmap Block / Free Space 관련 버그 Summary (19.4 ~ 19.31)

이 문서는 Oracle 19c Fixed Bug List(19.4 ~ 19.32)에서 **ASSM bitmap block의 free space 관리와
관련된 버그**(넓은 기준)를 Database Release Update 버전별로 취합한 문서입니다.

**대상 증상 (필터 기준):**
- ASSM 환경에서 수 GB 단일 테이블에 1건 INSERT 시 60~90초 이상 소요
- rollback 후 재수행하면 1초 이내 완료 (첫 실행이 stale FS1 블록들을 정리하기 때문)
- 원인: INSERT row 크기가 FS1(free 0~25%) 블록의 실제 가용 공간(row + PCTFREE 여유분)보다
  커서 insert 실패(reject) → free block을 찾기 위해 ASSM L1/L2 bitmap 블록을 반복 스캔

**포함 기준 (관련성이 조금이라도 있으면 포함):**
- ASSM bitmap(FS1~FS4) 상태 관리 / free block search 경로 (KTSP*/KTSB*/KTSJ 레이어)
- FSG(free space group) 캐시 / free list 관리
- Segment free space / PCTFREE / HWM 관련
- INSERT/DELETE/DML 성능 저하 (slow insert 계열)
- Segment space leak / space allocation
- ASSM segment repair / verify (진단·복구 도구 포함)

**제외 기준:**
- ASM diskgroup / ACFS / ADVM / KFOD 등 스토리지 계층의 free space
- Shared pool / SGA / PGA heap의 freelist, space leak (ORA-600 [729]/[730] 메모리 leak)
- GTT / HCC / Blockchain / Spatial / AQ / Streams 등 전용 오브젝트 한정 성능 이슈 중
  ASSM free space 경로와 무관한 것
- CTWR/ENQ CT global space management (switchover 관련), RAC GC freelist 등
- 순수 SQL 옵티마이저 / 분산 / 감사(Audit) 이슈

**태그:**
- **[ASSM]**: ASSM 명시 — bitmap 상태 불일치, segment repair 등
- **[KTSP]**: KTSB/KTSP/KTSJ space transaction 레이어 (ASSM bitmap block 처리 코드 경로)
- **[FSG]**: FSG(free space group) 캐시 / free list 관리
- **[FREE-SPACE]**: segment free space / PCTFREE / HWM / extent 관련
- **[SLOW-DML]**: INSERT/DELETE/DML 성능 저하
- **[SPACE-LEAK]**: segment space leak
- **[SEGMENT-REPAIR]**: DBMS_REPAIR.SEGMENT_FIX_STATUS / DBMS_SPACE_ADMIN repair·verify

## 리서치 결과 (참고): 증상과 정확히 일치하는 것은 구버전 버그 + MOS 문서

본 증상("첫 INSERT만 느리고 rollback 후 재수행하면 즉시 완료", FS1 블록 반복 reject/스캔)과
**1:1로 일치하는 공식 문서는 19c fixed bug list가 아니라 아래 자료**입니다:

- **Bug 7411960** - "A SIMPLE INSERT CAUSES LOTS OF 'DB FILE SEQUENTIAL READ' WAITS"
  FS1로 표시됐지만 실제로는 row를 수용할 공간이 없는 블록을 insert가 하나씩 읽어 reject.
  Oracle은 "expected behavior"로 종결. (19c fixed bug list 미수록, 11g 시절 버그)
- **MOS Doc ID 1263496.1 "INSERT slow on ASSM"** - 위 버그를 근거로 하는 공식 설명 문서.
  Workaround: 대량 DML 후 `EXEC DBMS_REPAIR.SEGMENT_FIX_STATUS('owner','table')`,
  또는 PCTFREE 상향. 진단: event 10320 level 3 + 10612 level 1 trace에서
  `ktspsrch` / `kdt_bseg_srch_cbk: failed ... mark full` 반복 확인.
- **Bug 13641076** - "High buffer gets for insert statement - rejection list does not fire"
  ASSM space search cache(rejection list) 관련. fix는 blacklist를 세션 기반으로 변경.
- **Bug 19791273** - "Poor UPDATE SQL performance due to space search cache for updates
  on ASSM segment" (workaround: event 10019)
- **Fix Control 32075777** (= Bug 32234161) - ASSM segment repair 활성화.
  `_fix_control='32075777:ON'` 설정 시 `x$ktsp_repair_list`가 채워지고 bitmap 상태 불일치가
  백그라운드로 보정됨 (19.19 사례 블로그에서 확인).

## 최종 정리: 증상과의 관련성이 가장 높은 대상

1. **BUG 30265523** (19.7 fix) — ASSM bitmap free 상태 미갱신. fix control 32075777과 연계된
   실사례(19.19)가 공개되어 있어 19c fixed bug list 내에서 증상과 가장 직접적으로 연결됨.
2. **BUG 32234161** (19.10 fix) — ASSM segment repair(fix control 32075777) 제어 버그.
   bitmap free space 상태 불일치 보정 메커니즘 자체.
3. **BUG 29695987** (19.10 fix) — ktspGetNextL1ForScan: 증상의 L1 bitmap 스캔 코드 경로.
4. **BUG 33195330** (19.18 fix) — ktspScanInit-L1: free block search 스캔 초기화 경로.
5. **BUG 31767852** (19.11 fix) — DBMS_REPAIR.SEGMENT_FIX_STATUS(MOS 1263496.1의
   workaround) 사용 후 KTSPBLKCHEKERROR.

단, 정확한 증상(첫 INSERT 60~90초, rollback 후 재수행 시 1초 이내)은 19c fixed bug list가
아닌 **Bug 7411960 + MOS Doc ID 1263496.1 "INSERT slow on ASSM"** 에 정확히 기술되어
있으며 Oracle은 이를 expected behavior로 분류합니다. 19c에서의 완화 수단은
`DBMS_REPAIR.SEGMENT_FIX_STATUS`, PCTFREE 상향, `_fix_control='32075777:ON'`(ASSM
segment repair) 등이며, 실제 적용 전 반드시 테스트 환경에서 검증이 필요합니다.
